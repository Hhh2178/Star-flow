# Stars Flow Toonflow Rebase Design

## Status

Draft. 本文档记录 Stars Flow 新主线的方向设计，用于决定是否以 Toonflow-app 作为基础改造成新的内部 AI 漫剧/短剧生产工具。

## Background

旧星环漫剧项目已经沉淀了较多需求、架构文档和业务规则，但当前实现出现明显问题：

- 前台和后台页面存在大量不可点击或无法完成真实动作的区域。
- 前端与后端接口契约不稳定，难以执行一次完整项目。
- 开发过程长期处于局部修补状态，真实可用体验没有随文档和架构复杂度同步增长。
- 系统缺少一条可反复验收的端到端生产主轴。

因此，旧星环漫剧实现不再作为默认主线。Stars Flow 以 Toonflow-app 为基础重新建立产品主线，旧星环漫剧作为需求和架构参考库。

## Product Positioning

Stars Flow 是面向内部十人团队的 AI 漫剧/短剧生产工具，第一阶段目标不是公开 SaaS，而是让团队可以真实完成从剧本输入到视频样片复核的生产闭环。

第一阶段优先服务内部团队：

- 统一管理项目、素材、任务和 Provider Key。
- 统一记录任务状态、成本和生成结果。
- 支持多人通过浏览器访问同一套系统。
- 保留后续 Electron 客户端连接云端中控的可能性。

## Why Toonflow As Base

Toonflow 已经具备 Stars Flow 最需要优先验证的产品能力：

- 小说、剧本、分镜、素材、视频的创作链路。
- ScriptAgent 和 ProductionAgent。
- Skill 文件化提示词体系。
- 画布式生产工作台。
- 本地和 Electron 封装基础。
- AI 短剧生产的可感知体验。

Stars Flow 应优先继承这些能直接形成生产体验的能力，而不是继续在旧星环漫剧的重架构上修补。

## Role Of Old Xinghuan Project

旧 `D:\codex\服务器\星环漫剧` 仓库作为参考库，优先提取：

- 产品目标和 MVP 链路。
- Provider-first 服务商管理思路。
- 项目预算、任务成本和额度显示规则。
- 视频质检、人工复核、重跑、上游回修规则。
- 后台管理信息架构。
- 星环漫剧视觉方向。

不直接迁入：

- 旧前端页面结构。
- 旧前后端接口形态。
- 旧 NestJS / FastAPI 复杂拆分。
- 过早平台化的配置版本中心、完整 RBAC、多租户和复杂状态机。

## Deployment Shape Decision

第一阶段采用服务器内部版，而不是优先给每位成员分发独立桌面应用。

### Option A: Internal Server Web App

团队统一访问服务器 Web 应用。

优点：

- 项目、素材、任务、成本和 Provider Key 集中管理。
- 十人团队协作简单。
- 更容易做权限、备份、日志和成本控制。
- 避免每台电脑单独配置模型 Key 和运行环境。

缺点：

- 需要服务器部署和运维。
- 本地大文件预览、剪辑和导出体验可能不如桌面应用。

### Option B: Standalone Desktop App

每个成员安装独立应用，本地运行 Toonflow 改造版。

优点：

- 继承 Toonflow 的本地工具体验。
- 本地素材处理方便。

缺点：

- Provider Key、素材、任务和成本分散。
- 团队协作困难。
- 版本更新、数据备份和问题排查成本高。
- 后续再接云端中控会形成同步和冲突问题。

### Option C: Desktop Client With Cloud Control

Electron 客户端连接云端中控。

优点：

- 兼顾桌面体验和云端统一管理。
- 适合后续做本地预览、缓存、FFmpeg、导出和上传。

缺点：

- 架构复杂度高于服务器 Web 版。
- 第一阶段实现成本较高。

### Recommendation

第一阶段采用 Option A：内部服务器 Web App。

第二阶段演进到 Option C：Electron 客户端连接云端中控。

不建议第一阶段采用 Option B。

## Development And Staging Workflow

Stars Flow 第一阶段建议同时保留本地开发环境和服务器 staging 环境。

本地开发环境位于 `D:\codex\服务器\Stars flow`，用于：

- clone 或 fork Toonflow。
- 修改代码。
- 调试前端、后端和生产链路。
- 提交 Git 变更。
- 使用 mock Provider 或低成本 Provider 做快速验证。

服务器 staging 环境用于：

- 十人团队通过浏览器试用。
- 验证真实账号、真实 Provider 配置和真实生成链路。
- 检查多人协作、素材存储、任务状态和成本记录。
- 提前暴露部署、权限、文件路径和长任务问题。

两套环境使用同一代码仓库，但必须隔离：

- `.env` 配置。
- Provider Key。
- 数据库或 SQLite 文件。
- 对象存储目录。
- 日志目录。
- 生成素材和付费任务。

推荐流程：

1. 本地完成小步开发和基础验证。
2. 提交 Git。
3. 服务器拉取指定提交。
4. 在服务器执行 staging smoke。
5. 十人团队试用并反馈。
6. 反馈只回到本地开发，不直接在服务器手改代码。

该流程允许我们既保持本地开发效率，又尽早验证团队内部真实使用场景。

## Phase 1 MVP Scope

第一阶段只做内部可用闭环：

1. 管理员登录。
2. 管理员配置 Provider 和模型。
3. 团队成员登录。
4. 创建项目。
5. 导入小说、题材或剧本。
6. 生成剧本结构。
7. 生成角色、场景和资产。
8. 生成分镜。
9. 生成图片素材。
10. 生成视频样片。
11. 人工复核视频。
12. 对问题节点进行重跑。
13. 记录任务状态和基础成本。

## Visual Direction

Stars Flow 保留 Toonflow 的功能密度和创作工作台效率，但视觉上向星环漫剧靠拢：

- 从普通工具界面升级为生产中台质感。
- 项目级页面强调流程、状态、素材和复核。
- 后台页面强调 Provider、模型、成本和任务监控。
- 页面应减少无效装饰，突出可点击动作、状态反馈和下一步操作。
- 所有关键按钮必须连接真实动作，不保留看起来可用但不能完成流程的空按钮。

建议的主要界面结构：

- 顶部：项目、任务、成本、用户入口。
- 左侧：项目流程或后台功能导航。
- 中央：画布、分镜、素材或任务主工作区。
- 右侧：属性、生成参数、复核意见和操作记录。

## Technical Direction

第一阶段优先降低工程风险：

- 先让 Toonflow 在 Stars Flow 下稳定运行。
- 尽量少动创作链路核心。
- 先增强登录、Provider 配置、任务状态和成本记录。
- 数据层是否从 SQLite 迁移 PostgreSQL，放到验证后决定。
- 不急于引入旧星环漫剧的 NestJS + FastAPI 分层。

建议的演进顺序：

1. Clone / fork Toonflow 到 Stars Flow。
2. 跑通原始 Toonflow。
3. 建立 Stars Flow 品牌和视觉壳。
4. 做服务器内部部署模式。
5. 加固登录和配置。
6. 接入首批 Provider 配置。
7. 跑通端到端生产链路。
8. 补任务、成本、复核和重跑。
9. 再评估是否迁移 PostgreSQL 或拆服务。

## Validation Criteria

7-10 天验证期必须证明：

- Stars Flow 可以在服务器或本机服务模式稳定启动。
- 至少 3 个团队账号可以登录并创建项目。
- 管理员可以配置至少一个文本、图片或视频 Provider。
- 一个项目可以从输入剧本推进到视频样片。
- 视频样片可以进入人工复核。
- 失败任务或不满意结果可以重跑。
- 页面上的关键按钮都能触发真实动作。
- 生成任务有状态反馈。
- 基础成本或调用记录可以被查看。

如果以上目标无法完成，说明 Toonflow 改造成本高于预期，需要重新评估。

如果以上目标完成，Stars Flow 升级为正式新主线，旧星环漫剧实现冻结为参考。

第一阶段限定为内部十人团队使用，不做外部分发。
