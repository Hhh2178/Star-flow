# GitHub And CI Policy

## Purpose

Define the authoritative GitHub branch and automated verification rules for the private Stars Flow Monorepo.

## Repository

- Authoritative remote: `https://github.com/Hhh2178/Star-flow`.
- Visibility: private.
- Default branch: `main`.
- Long-lived branches: `main` and `dev` only.
- Short-lived work branches start from `dev` and are removed after integration.

## Required Checks

The `CI` workflow publishes three required checks:

| Check | Scope |
| --- | --- |
| `Governance` | Documentation/harness contracts and release-layout tests |
| `App` | Frozen App install, TypeScript, deterministic R2/R3 suites, migrations and production build |
| `Web` | Frozen Web install, source tests, identity/boundary checks, type check and Creator/Admin builds |

CI must never load production environment files, Provider credentials, real user data or paid validation flags. Real Provider validation and deployment remain manually authorized operations.

## Main Branch Protection

`main` must:

- require `Governance`, `App` and `Web` to pass;
- require the branch to be current before integration;
- reject force pushes and branch deletion;
- require conversation resolution;
- preserve linear history.

`dev` remains the integration branch. A complete, locally verified `dev` commit may advance `main` only after CI passes and any required staging gate is recorded.

## Dependency Policy

- App CI uses Node.js `20.20.0`, Yarn 1 and `yarn install --frozen-lockfile --ignore-engines` because the Electron dependency graph contains stricter transitive engine declarations.
- Web CI uses Node.js `20.20.0`, Yarn 1 and `yarn install --frozen-lockfile`.
- Lockfiles must not be regenerated by CI.
- GitHub Actions receive read-only repository contents permission unless a future workflow has a documented need for more.

## Failure Policy

- Do not bypass a failed required check by pushing generated output or disabling a test.
- Reproduce the failing job locally using the matching package script.
- Treat flaky tests as defects; record and repair them instead of adding unconditional retries.
- A CI outage may delay integration but does not authorize direct unverified production deployment.
